LLM chapter: two streams after decoding

Proposal of 2026-10-28 (DECISIONS #105), updated 2026-11-12 to what has happened since (section 0). Deck labels follow the teaching order of DECISIONS #113: LLM-2 Decoding, LLM-3 Embeddings, LLM-4 Attention, LLM-5 the block, LLM-6 Transformers in the world. Built from llms/LLM_CHAPTER_PLAN.md, the deck folders under llms/, llms/04_rag, ml/ch18_agents, ml/ch13_audio, DECISIONS #74 and #96, and a web check (section 11). Session numbers are planning numbers.

In short
  • The shared trunk is done: LLM-1, its practical, LLM-2 Decoding (moved up from session 6, even before embeddings), and B0, the first real API call, in which every knob from LLM-2 is a request field. Next to teach: B0b, job ads to checked JSON (built).
  • Then two streams alternate, one session each. A opens the box with the built decks in order, from LLM-3 Embeddings. B is a workshop line: B0b, prompting, tool calls and MCP, search, RAG, evals, agents, voice, local models, fine-tuning, a capstone. What comes right after B0b is still open (Q9).
  • Built decks are reused, not rewritten: LLM-10 and L41 to L44, plus parts of LLM-11, L33 and L35, become stream B's slides. Built so far: PR-1, B0 and B0b. Still to build: 11 notebooks and one short voice deck.
  • Count: 27 sessions in all, 4 delivered and 23 to go (22 without the optional B8). 14 are hands-on, against 2 in the old single-line plan. It only works if each week really has a free practical slot (Q2).

2. Why change the plan

The plan as it stood on 2026-10-28 (LLM_CHAPTER_PLAN.md, sections 5.0 and 6) has 17 lectures left in one line: LLM-2 to LLM-14, with the RAG and agents decks (L41 to L44) in the middle, after LLM-11. Hands-on work is two practicals and one homework: P1, a tiny Armenian GPT after LLM-7/8; P2, a QLoRA fine-tune after LLM-13; the quantization-ladder homework after LLM-12. None was built: there was no notebook under llms/. Neither practical had students call a model the way a job will ask them to, and the first industry-shaped topic, RAG, arrived at session 12.

The proposal moved the first API call to session 5; with decoding moved up further, it came at session 4 (B0, delivered). 14 of the 26 sessions after LLM-1 are hands-on.

The same split already exists in the most-used open LLM curriculum

Maxime Labonne's llm-course splits into "The LLM Scientist" and "The LLM Engineer" (section titles below are from its README, read 2026-10-28). The mapping is close:

One real difference: his two tracks are separate roadmaps for two kinds of reader. Here both run for the same students. That is a different bet, and it is Q1.

What the split buys besides practicals

Stream B keeps raising questions that stream A answers a few weeks later (section 6). "Why did the cached part of my prompt cost less?" is a better way into the KV cache in LLM-14 than any cold open we can write. Today the theory has to create its own motivation; with B running alongside, students arrive with the question already asked.

Moving decoding up (done)

Decoding (LLM-6 when this was proposed) was built as session 6, after the attention decks. Only four spots leaned on them; #109 turned them into forward pointers ("how: LLM-4") and kept speculative decoding in the deck at the instructor's word. Everything else treats the model as something that hands you a distribution, which is all a decoding lecture needs.

The decoding deck's interview (2026-10-05) cut the API-parameter table from the source deck, declined "providers locking knobs", and chose "no hands-on in the slides". The plan kept that: the table below and the locked-knob point went into B0's notebook (#111), not into the deck.

Every request field is a frame in LLM-2

The table B0 was built around. Field names follow the OpenAI-style chat API; other providers use close variants.

OpenAI forum users report GPT-5 accepts only the default temperature, and that GPT-5.1 allows temperature, top_p and logprobs when reasoning effort is "none" (user reports, not docs). Anthropic's docs: Claude 4.7 and later reject a manual budget_tokens and take thinking: {type: "adaptive"} with an effort setting (read 2026-10-28). Re-check both before B0 is taught again.

5. Stream B: build with it

Format. Each workshop: about 25 minutes of slides taken from a built deck, about 60 minutes in a notebook, and an executed solution copy afterwards (the same pattern as the biopsy notebook, DECISIONS #80 and #81). Each workshop builds on the code of the one before: B1's client is the one B9 points at localhost, B4's search becomes a tool in B6, B6's agent gets a voice in B7, B5's evals score B10's fine-tune, and B11 ships one of them.

Framework-free first. Every pattern is written by hand once (a raw request, a 40-line agent loop, cosine similarity in numpy), then shown in one framework. Which framework is a separate decision per session (Q7). Tools change faster than the ideas under them, as DECISIONS #74 put it; the hand-written version is the part that will still be true in a year.

8. What it costs, what can go wrong
  1. It needs the slots. DECISIONS #96 (2026-10-24) removed the RNN practical because "the instructor has no session left for a practical". This plan has 13 workshops (B0, B0b, B1 to B11) plus PR-1; three are done. If the practical day is not actually free, the plan does not fit, and the fix is cutting B, not squeezing it (Q2, Q6).
  2. Build work. 11 notebooks still to build (B1 to B11), each with data, a solution copy and a short slide pull, plus one new voice deck. A guess, not a measurement: about one working session per notebook to build and test, so roughly 11 build sessions, more for B7 (audio on Windows) and B10 (Colab).
  3. Stream B goes stale fast. SDKs, model names, prices and free tiers change monthly. Every notebook needs pinned versions (==) and a re-run before each delivery. Budget that re-check; it is not optional.
  4. Model access is a money decision (Q3). Students without a card, free tiers that change without notice, local models that crawl on weak laptops, and realtime voice that needs a hosted API.
  5. The RAG decks do not fit a workshop. L41, L42 and L43 have 55, 59 and 55 frames, with the full BM25 and contrastive derivations the RAG chapter's teaching stance asked for. Condensing them to ~25-minute pulls throws away reviewed work; keeping them adds 3 sessions (Q4).
  6. The course map changes. llms/00_shared/py_src/llm_roadmap.py's SESSIONS list already puts decoding second (#109); it changes again when the streams start, and every deck's "Where we are" frames get recompiled. The "life of a model" row still holds as a picture; only what is lit when changes.
  7. Pointer edits in built decks. Done for the reorder (#109, #112): decoding ends on B0, LLM-6 ends on LLM-7, LLM-3's callbacks follow decoding. Left: LLM-11's "Next: the RAG chapter" frame goes (RAG happens earlier, in B).
  8. Reopened decisions. DECISIONS #74 (no runtime taught) reopens the moment B9 runs a local model; its own "what would change this" says exactly that. Chapter plan section 2 (RAG and agents inside the chapter's run, after LLM-11) is replaced.
  9. Armenian voice is unmeasured. AssemblyAI, Deepgram and Gladia list Armenian speech-to-text on their sites. Those are vendor claims. B7 measures word error rate on our own recordings before anyone promises an Armenian voice agent.
  10. Students may rank B above A ("why learn attention if I can call the API?"). The defence is section 6: every A lecture opens with a thing they hit in B. If that link is not made in the room, the split weakens the theory.

9. Decisions for you (Q1 to Q9)

Q1. What does "two paths" mean for students?

  1. Everyone takes both, alternating: one A lecture and one B workshop a week. My lean: one instructor, B needs A at three points (section 6), and jobs want both.
  2. Students pick one stream (Labonne-style). Halves what each student sees; you would teach both anyway.
  3. B as one block after A ends. Simplest, but brings back the problem: no API until the end.

Flips to (b) if the cohort clearly splits into "wants a job" and "wants research", and you have two slots a week to run them side by side.

Q2. How many sessions a week does this part get, and is the practical day free?

Not mine to guess: #96 says there was no slot for the RNN practical a week ago. The answer decides whether this is a 13-week or a 25-week plan.

Q3. Where do the students' model calls go? (fundamental, your call)

Decided 2026-11-06 (DECISIONS #110): OpenRouter through the openai SDK, one key. That is option (d)'s client; B9's local server is still to come.

  1. One hosted API with a course budget or key policy. Simplest to teach; costs money.
  2. Free tiers of hosted providers. No money; rate limits and terms change without notice.
  3. Local open models only. Free and private; slow on weak laptops, no realtime voice, reopens #74 for every session.
  4. One OpenAI-compatible client in every notebook: hosted by default, the same code pointed at a local server in B9 (Ollama, llama.cpp's server and vLLM all speak this interface). My lean.

Hard to reverse: once 13 notebooks are written against one SDK, switching is a rewrite. The client interface is the sticky part, more than the provider.

Q4. The RAG decks inside a workshop stream

  1. Condensed pulls (~25 minutes each) for B3, B4 and B5; the full decks stay as reading. My lean: workshop time goes to building.
  2. Keep L41 to L43 as full lectures inside stream B (+3 sessions).
  3. L41's BM25 and contrastive derivations move to stream A as one theory lecture; L42 and L43 are condensed.

Q5. Three built decks change place. Approve each separately

  1. Done, and further (#109): decoding moved from session 6 to session 3, before embeddings; it is LLM-2 now.
  2. LLM-10 Prompting moves whole into B1.
  3. LLM-11's three LLM-as-judge frames move into B5.

(b) and (c) are open. Nothing gets touched until you say yes to the specific item.

Q6. Which B sessions stay?

All eleven, plus B0b (built), are on the diagram. If time is short, cut in this order: B8 vision (already optional), merge B9 into B10, merge B3 into B4. B7 voice stays, since you named it.

Q7. Frameworks: hand-written first, one framework after, chosen per session later?

Agents, voice, vector store and deployment each have several real options (for voice, for example, Pipecat and LiveKit Agents as open-source runtimes, or a provider's speech-to-speech API). I would bring 2 to 4 options with trade-offs when each session is built, not pick now.

Q8. LLM-3 Embeddings: whole, or split?

  1. Whole, as built (90 pages after #112's review). My lean: it is built and reviewed, and its long-context part (lost in the middle, context rot) is exactly what B4 needs.
  2. Split: embeddings stay, the RoPE half moves after LLM-4 (RoPE rotates queries and keys, which LLM-4 introduces). Its original reason, reaching the API sooner, is gone: B0 already happened.

Q9. What comes right after B0b? (new, 2026-11-12)

Decided the same day (DECISIONS #115): B0b was shelved, and the next session is a two-session tools practical (tool calls, MCP, skills, orchestration), built in llms/03_tools_agents/; LLM-3 comes before search. The options and the reasoning: llms/NEXT_STRETCH_OPTIONS.html.

Left open in #109 ("decide later") and parked in DEFERRED_TODO.md to be decided before B0 was taught. B0 is taught now, and B0b is the next session either way.

  1. LLM-3 Embeddings, then A and B alternate as drawn. My lean: B3 needs LLM-3, and #109 already said the theory decks "open the box afterwards"; alternating keeps both threads moving.
  2. More workshops first (B1 prompting, B2 tool calls), then LLM-3. Keeps the hands-on run going while the API is fresh; the theory decks then come as a longer block.

Flips to (b) if the class clearly engages more with the workshops and the theory can wait two weeks.

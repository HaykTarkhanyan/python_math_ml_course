LLM chapter: two streams after decoding

Proposal, 2026-10-28. Nothing in the repo has changed. Built from llms/LLM_CHAPTER_PLAN.md, the deck folders under llms/, ml/ch17_rag, ml/ch18_agents, ml/ch13_audio, DECISIONS #74 and #96, and a web check (section 11). Session numbers are planning numbers.

In short
  • Everyone does a short shared trunk: LLM-1 (done), a tokenization practical, LLM-2, then LLM-6 Decoding moved up from session 6 to session 4, then B0, a first real API call in which every knob from LLM-6 shows up as a request field.
  • Then two streams alternate, one session each. A continues the theory with the built decks in their current order. B is a workshop line: prompting, tool calls and MCP, search, RAG, evals, agents, voice, local models, fine-tuning, a capstone.
  • Built decks are reused, not rewritten: LLM-10 and L41 to L44, plus parts of LLM-11, L33 and L35, become stream B's slides. New work: 13 notebooks and one short voice deck.
  • Cost: 25 sessions left instead of about 19, with 13 hands-on sessions instead of 2 (and neither of those 2 is built yet). It only works if each week really has a free practical slot (Q2).

2. Why change the plan

Today's plan (LLM_CHAPTER_PLAN.md, sections 5.0 and 6) has 17 lectures left in one line: LLM-2 to LLM-14, with the RAG and agents decks (L41 to L44) in the middle, after LLM-11. Hands-on work is two practicals and one homework: P1, a tiny Armenian GPT after LLM-7/8; P2, a QLoRA fine-tune after LLM-13; the quantization-ladder homework after LLM-12. None is built: there is no notebook under llms/. Neither practical has students call a model the way a job will ask them to, and the first industry-shaped topic, RAG, arrives at session 12.

The proposal moves the first API call to session 5 and gives 13 of the next 25 sessions to hands-on work.

The same split already exists in the most-used open LLM curriculum

Maxime Labonne's llm-course splits into "The LLM Scientist" and "The LLM Engineer" (section titles below are from its README, read 2026-10-28). The mapping is close:

One real difference: his two tracks are separate roadmaps for two kinds of reader. Here both run for the same students. That is a different bet, and it is Q1.

What the split buys besides practicals

Stream B keeps raising questions that stream A answers a few weeks later (section 6). "Why did the cached part of my prompt cost less?" is a better way into the KV cache in LLM-14 than any cold open we can write. Today the theory has to create its own motivation; with B running alongside, students arrive with the question already asked.

Moving LLM-6 is cheap, but it was not built to come first

LLM-6 was always session 6, after the attention decks (its provenance comment says so). It leans on them in only three places: line 118 ("LLM-5: each step ends in logits, softmax..."), line 713 (speculative decoding uses LLM-4's causal mask) and the Transformer Explainer link it calls "LLM-3's". Everything else treats the model as something that hands you a distribution, which is all a decoding lecture needs.

The LLM-6 interview (2026-10-05) cut the API-parameter table from the source deck, declined "providers locking knobs", and chose "no hands-on in the slides". This proposal respects that: the table below and the locked-knob point go into B0's notebook, not into the deck.

5. Stream B: build with it

Format. Each workshop: about 25 minutes of slides taken from a built deck, about 60 minutes in a notebook, and an executed solution copy afterwards (the same pattern as the biopsy notebook, DECISIONS #80 and #81). Each workshop builds on the code of the one before: B1's client is the one B9 points at localhost, B4's search becomes a tool in B6, B6's agent gets a voice in B7, B5's evals score B10's fine-tune, and B11 ships one of them.

Framework-free first. Every pattern is written by hand once (a raw request, a 40-line agent loop, cosine similarity in numpy), then shown in one framework. Which framework is a separate decision per session (Q7). Tools change faster than the ideas under them, as DECISIONS #74 put it; the hand-written version is the part that will still be true in a year.

8. What it costs, what can go wrong
  1. It needs the slots. DECISIONS #96 (2026-10-24) removed the RNN practical because "the instructor has no session left for a practical". This plan adds 12 workshops plus PR-1. If the practical day is not actually free, the plan does not fit, and the fix is cutting B, not squeezing it (Q2, Q6).
  2. Build work. 13 notebooks, each with data, a solution copy and a short slide pull, plus one new voice deck. A guess, not a measurement: about one working session per notebook to build and test, so roughly 13 build sessions, more for B7 (audio on Windows) and B10 (Colab).
  3. Stream B goes stale fast. SDKs, model names, prices and free tiers change monthly. Every notebook needs pinned versions (==) and a re-run before each delivery. Budget that re-check; it is not optional.
  4. Model access is a money decision (Q3). Students without a card, free tiers that change without notice, local models that crawl on weak laptops, and realtime voice that needs a hosted API.
  5. The RAG decks do not fit a workshop. L41, L42 and L43 have 55, 59 and 55 frames, with the full BM25 and contrastive derivations the RAG chapter's teaching stance asked for. Condensing them to ~25-minute pulls throws away reviewed work; keeping them adds 3 sessions (Q4).
  6. The course map changes. llms/00_shared/py_src/llm_roadmap.py's SESSIONS list must match the new order, and every deck's "Where we are" frames get recompiled. The "life of a model" row still holds as a picture; only what is lit when changes.
  7. Pointer edits in built decks. LLM-2's "Next (LLM-3)" becomes LLM-6; LLM-6's "Next (LLM-7)" becomes B0 and LLM-3; LLM-5's "Next (LLM-6)" becomes LLM-7; LLM-11's "Next: the RAG chapter" frame goes (RAG already happened in B).
  8. Reopened decisions. DECISIONS #74 (no runtime taught) reopens the moment B9 runs a local model; its own "what would change this" says exactly that. Chapter plan section 2 (RAG and agents inside the chapter's run, after LLM-11) is replaced.
  9. Armenian voice is unmeasured. AssemblyAI, Deepgram and Gladia list Armenian speech-to-text on their sites. Those are vendor claims. B7 measures word error rate on our own recordings before anyone promises an Armenian voice agent.
  10. Students may rank B above A ("why learn attention if I can call the API?"). The defence is section 6: every A lecture opens with a thing they hit in B. If that link is not made in the room, the split weakens the theory.

9. Decisions for you (Q1 to Q8)

Q1. What does "two paths" mean for students?

  1. Everyone takes both, alternating: one A lecture and one B workshop a week. My lean: one instructor, B needs A at three points (section 6), and jobs want both.
  2. Students pick one stream (Labonne-style). Halves what each student sees; you would teach both anyway.
  3. B as one block after A ends. Simplest, but brings back the problem: no API until the end.

Flips to (b) if the cohort clearly splits into "wants a job" and "wants research", and you have two slots a week to run them side by side.

Q2. How many sessions a week does this part get, and is the practical day free?

Not mine to guess: #96 says there was no slot for the RNN practical a week ago. The answer decides whether this is a 13-week or a 25-week plan.

Q3. Where do the students' model calls go? (fundamental, your call)

  1. One hosted API with a course budget or key policy. Simplest to teach; costs money.
  2. Free tiers of hosted providers. No money; rate limits and terms change without notice.
  3. Local open models only. Free and private; slow on weak laptops, no realtime voice, reopens #74 for every session.
  4. One OpenAI-compatible client in every notebook: hosted by default, the same code pointed at a local server in B9 (Ollama, llama.cpp's server and vLLM all speak this interface). My lean.

Hard to reverse: once 13 notebooks are written against one SDK, switching is a rewrite. The client interface is the sticky part, more than the provider.

Q4. The RAG decks inside a workshop stream

  1. Condensed pulls (~25 minutes each) for B3, B4 and B5; the full decks stay as reading. My lean: workshop time goes to building.
  2. Keep L41 to L43 as full lectures inside stream B (+3 sessions).
  3. L41's BM25 and contrastive derivations move to stream A as one theory lecture; L42 and L43 are condensed.

Q5. Three built decks change place. Approve each separately

  1. LLM-6 Decoding moves from session 6 to session 4 (three line edits, section 3).
  2. LLM-10 Prompting moves whole into B1.
  3. LLM-11's three LLM-as-judge frames move into B5.

Nothing gets touched until you say yes to the specific item.

Q6. Which B sessions stay?

All eleven are on the diagram. If time is short, cut in this order: B8 vision (already optional), merge B9 into B10, merge B3 into B4. B7 voice stays, since you named it.

Q7. Frameworks: hand-written first, one framework after, chosen per session later?

Agents, voice, vector store and deployment each have several real options (for voice, for example, Pipecat and LiveKit Agents as open-source runtimes, or a provider's speech-to-speech API). I would bring 2 to 4 options with trade-offs when each session is built, not pick now.

Q8. LLM-2 in the trunk: whole, or split?

  1. Whole, as built (77 frames). My lean: it is built and reviewed, and its long-context part (lost in the middle, context rot) is exactly what B4 needs.
  2. Split: embeddings stay in the trunk, the RoPE half moves into A after LLM-3 (RoPE rotates queries and keys, which LLM-3 introduces). Reaches the API a little sooner.
